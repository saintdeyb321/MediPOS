# MediPOS backend

Requires the .NET 10 SDK. This local machine has no Docker and will not install it. Do not check/start Docker or execute PostgreSQL/Testcontainers locally. B0.1 is complete under the local gate below; PostgreSQL integration tests remain available for another environment.

Configure `ConnectionStrings:MediPosDatabase` outside source control before starting the API. For local development, from `backend/`:

```sh
dotnet user-secrets set "ConnectionStrings:MediPosDatabase" "<connection-string>" --project src/MediPOS.Api
dotnet run --project src/MediPOS.Api
```

Alternatively, set the environment variable `ConnectionStrings__MediPosDatabase`. Startup fails with a configuration error when the connection string is missing or blank. No database is created or migrated automatically.

The local launch profile uses `http://localhost:5080`. `GET /health` reports process health; `GET /health/ready` checks the guarded runtime PostgreSQL dependency. Neither authorizes a production pilot. The OpenAPI document is served at `/openapi/v1.json` only in Development.

```sh
dotnet restore
dotnet build
dotnet test tests/MediPOS.UnitTests
dotnet test tests/MediPOS.ArchitectureTests
dotnet format --verify-no-changes
```

The integration suite is prepared for an environment with a Docker-compatible engine and Linux containers. It shares one isolated `postgres:18-alpine` container with a random password, applies the migration to an empty database, and uses distinct tenant IDs to isolate test data. It covers the smoke connection, persistence/history, tenant-bound foreign keys, unique current licenses, constraints, state changes, append-only history and concurrent renewal. These tests are not part of the local gate and have not been validated here.

Migration tooling (no database connection is needed to scaffold migrations or check the model):

```sh
dotnet tool restore
dotnet ef migrations has-pending-model-changes --project src/MediPOS.Infrastructure --startup-project src/MediPOS.Infrastructure
```

The first migration is `InitialTenancyLicensing`, in Infrastructure. The design-time factory configures Npgsql without credentials for offline model work; it also accepts `ConnectionStrings__MediPosDatabase` when tooling is used in a database-enabled environment. The API never applies migrations at startup.

The second migration, `AddLegalEntitiesAndBranches`, adds tenant-owned legal entities and branches. Branch creation locks the current license row in a Read Committed transaction before checking its validity and counting branches; the licensing and branch ports share one scoped DbContext. New branches have no hub role; `SetMainHubBranch` moves it atomically using the same lock and a partial unique index. Real PostgreSQL tests for these constraints and concurrent provisioning are prepared but not executed locally.

TenancyLicensing retains its five existing application handlers and tenant/license-scoped persistence port. CreateTenant now has an additional idempotent application orchestrator for the independently enabled platform HTTP boundary; RequestTenantPurge remains internal. RenewLicense, SuspendLicense and ReactivateLicense retain their existing HTTP behavior. Every handler retains its own platform authorization and audit checks. The operation gate uses the interval `[starts_at, expires_at)`. Reactivation requires Suspended and an explicit Trial/Active/Grace target; renewal preserves status. Identical renewals and repeated suspension/purge requests are no-ops. Cancelled/PurgePending/Purged cannot be renewed or reactivated. Purge requests persist PurgePending and history; physical deletion and FR-LIC-005/A18 completion remain pending.

The fifth migration, `AddAuditFoundation`, adds tenant-private `audit_logs` with UUIDv7 IDs, UTC timestamps, bounded action/entity codes, minimal `jsonb` snapshots, tenant/time indexes and forced RLS. Its policies permit tenant-scoped SELECT/INSERT only. Grant the runtime role **SELECT and INSERT only** on this table, without UPDATE, DELETE or TRUNCATE; migration credentials remain separate. Domain has no audit update/delete operations, and DbContext rejects modified/deleted audit entries.

The twelve existing tenant/license, legal entity/branch and membership mutations persist business changes and audit in the same SaveChanges or existing provisioning transaction, including bulk updates/deletes. Failed audited saves clear staged entries; transaction disposal rolls back earlier bulk statements. Idempotent requests produce no new change event. Internal commands require a nonempty actor ID supplied by an authenticated server caller, never a free HTTP body; audit has no mandatory membership FK. Correlation comes from the server Activity trace or a generated server ID. Application errors have stable codes/categories; central API handling emits Problem Details with code/trace and 400/403/404/409, or a sanitized 500. Unexpected-error logs contain only exception type and server trace. The authentication and platform opt-ins below define their rate-limit policies; search/sync/integration/commercial routes remain unpublished.

Real PostgreSQL audit tests cover migration, restricted role privileges, tenant isolation, cross-tenant insertion, append-only enforcement, successful atomic writes, rollback after audit failure and pooled connection reuse. They are prepared and unexecuted locally.

The sixth migration, `AddCatalogFoundation`, creates global categories/products/medicine profiles and tenant-private business products. Medicine composition is a defensive list of supplied ingredient names stored as PostgreSQL `text[]`; strength/form/route/registration are preserved without automatic parsing or equivalence. Tenant medicine data shares the business product row through an owned value object. Medicine requires composition, strength and form; Retail has no pharmaceutical profile. All prices are tenant-only `numeric(18,4)`; inputs requiring rounding or exceeding that precision are rejected. Internal codes are trimmed and unique per tenant with exact comparison. Barcodes are optional and not unique.

Six internal Catalog handlers cover platform category/global creation and tenant creation from global/local data, prices and activation. Global and tenant ports are distinct; callers must authorize platform administration or tenant operations before HTTP exposure. Tenant/actor IDs must come from authenticated server context. Tenant writes validate the current license under the existing provisioning transaction, and three business product audit actions commit with the product. Query filters, owned-column write guards and forced RLS protect business products; global tables remain visible without a tenant. Runtime credentials and global write authorization remain distinct concerns. Real PostgreSQL catalog constraint/isolation/atomicity/pooling tests are prepared and unexecuted locally. M0 is implemented locally; full release validation remains pending the external PostgreSQL suite.

Tests use `xunit.v3.mtp-off` with VSTest. Unit tests cover domain rules and application behavior; architecture tests continue enforcing the existing project dependency rules.

The third migration, `AddIdentityAccess`, adds global Google-subject users, tenant memberships, branch assignments and local work windows. Roles/day codes are explicit strings; assignments and schedules use composite tenant foreign keys. Membership creation and all membership configuration changes reuse the current-license row lock and transaction. Only active memberships are unique per tenant/user; an inactive membership remains referencable if a new membership is created. Two active Owners is enforced by the serialized application path, not by a database trigger.

The fourth migration, `AddTenantRowLevelSecurity`, enables and forces RLS on licenses, license history, legal entities, branches, memberships, assignments and schedules. `ITenantDataContext` selects one tenant per DI scope; a different tenant needs a new scope. Selection limits data and grants no authorization: `ResolveAccessContext` still checks the authenticated user and B0.4 policy. Normal EF reads fail closed without a tenant, and tracked private writes must match both original and current tenant ownership. Tenant remains a platform root, and User remains global; neither receives RLS or a query filter here. Their administration requires authorized platform/identity callers.

Connection and command interceptors parameterize `medipos.tenant_id`, explicitly writing an empty setting without a scope. They cover pooled checkout, selection after opening and transaction rollback; Npgsql connection pooling remains enabled. Use a production runtime role with **NOSUPERUSER and NOBYPASSRLS**, no table/schema ownership or DDL privileges; use separate migration credentials. FORCE subjects ordinary table owners to policies but cannot constrain superusers/BYPASSRLS ([PostgreSQL documentation](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)). The integration harness migrates using its isolated container administrator and runs application/RLS paths with an ephemeral restricted role. Administrator contexts are reserved for independent constraint/filter checks, never RLS assertions. All PostgreSQL tests remain prepared and unexecuted locally.

Authentication is an explicit server boundary: `IVerifiedGoogleIdentitySource` supplies claims only after OIDC verification, and `IAuthenticatedMediPosUser` supplies the internal user ID only from a validated MediPOS server session. B8.6.1 provides the production adapters and limited authentication routes through opt-in Google OIDC configuration below; they remain disabled by default. Internal provisioning handlers still require independent administrative authorization before HTTP exposure.

Authorization reads current membership, license, branch assignment and schedule in one tenant-bound PostgreSQL statement and returns stable access codes plus context. Requested tenant/branch IDs only select a target; they never establish identity or permission. B0.5 can consume this policy, re-evaluated for each protected operation with server time. Work windows use `TimeOnly`, America/Lima through .NET `TimeZoneInfo`, and the interval `[start, end)`; overnight windows are rejected. Boundaries must fit PostgreSQL microsecond precision. Owners bypass assignment/schedule checks but still need active membership and a valid license; any selected branch must belong to the tenant. Deactivation is idempotent and keeps user, membership, assignments and schedule; inactive configuration cannot be replaced. PostgreSQL constraint, atomic-replacement, authorization-query and concurrent Owner tests are prepared and remain unexecuted locally.

## Observability and operability — B8.4

With authentication disabled, the HTTP surface remains `/health`, `/health/ready` and Development-only OpenAPI. B8.6.1 adds only the configured authentication routes below. There is no metrics/commercial endpoint or enabled CPE provider. Health is a technical diagnostic, not pilot approval.

- `/health`: process liveness, 200 `Healthy`, without resolving or opening PostgreSQL.
- `/health/ready`: restricted commercial runtime and empty tenant scope, mandatory role guard, a read-only transaction and `SELECT 1`; 200 `Healthy` or 503 `Unhealthy`. No migration, data scan, mutation or administrative credential. `Observability__Readiness__TimeoutSeconds` defaults to 3 (1–10); SQL commands have a 2-second timeout and caller cancellation is honored. Two probes per process may run concurrently; no waiting queue. Saturation returns 503 before opening a connection, so a 503 alone does not prove PostgreSQL is down.
- Both responses use `Cache-Control: no-store`, including limiter rejections. Bodies expose no dependency details. `X-Correlation-ID` shares the validated W3C/server trace with Problem Details; `X-Request-ID` is generated by the server. Free correlation/tenant headers and baggage grant no authority.

The initial VM needs TLS termination, a non-public application bind, trusted proxy configuration, monitor access to these paths and bounded polling (initial proposal: every 30 seconds, client timeout above the server deadline). Restrict readiness to the hosting monitor at the proxy; the application returns only aggregate status but does not authenticate this diagnostic. Do not enable broad forwarded-header trust. Hosting must configure access restrictions, process supervision, secret storage, log rotation/retention and protected operator access. These deployment controls are not configured or validated here.

From that approved host, use the deployment's real base address; these commands were not executed against PostgreSQL locally:

```powershell
curl.exe --fail --max-time 5 --include "$env:MEDIPOS_BASE_URL/health"
curl.exe --fail --max-time 5 --include "$env:MEDIPOS_BASE_URL/health/ready"
```

The native console provider queues JSON output using the `medipos-json` projection: UTC timestamp, level, category, numeric EventId, stable module/EventId code, safe scalar state and validated trace/request IDs. It never formats arbitrary messages, raw exception messages/stacks/data, SQL, connection strings, HTTP paths/bodies/headers or baggage. Application schemas retain counts, outcomes/duration and exception type; only the existing expiration-system schema may include its trusted tenant UUID. Unknown fields are omitted. Framework Warning/Error/Critical events retain category/EventId and exception type with a generic message, requiring a protected separate investigation for detailed diagnosis. Native raw HTTP lifecycle logging/scopes are replaced by events 8000/8001; successful health polling has no per-request application log. Unexpected failures retain event 1; expiration started/completed/tenant-failed/run-failed use 4103/4101/4100/4102. Environment overrides cannot select an unsafe console formatter or re-enable verbose protected sources. Other exporters/providers must apply the same projection before activation.

Configure application severity with `Logging__LogLevel__MediPOS` (Information initially). Console output and sanitized warning floors are enforced for framework/database sources. Its native queue is bounded to 512 records with `DropWrite`: slow output may lose technical logs but cannot block business work on a full logging queue; these logs never replace financial/audit history. Expiration scheduling remains opt-in with `Notifications__ExpirationAlerts__Enabled=true`: catch-up at startup, then the existing next-day 05:00 America/Lima schedule, without a monitoring worker. Logging/listener failures are best effort and cannot change a completed operation. No database stores technical logs and no exporter/collector/server is mandatory. Shipping, rotation, storage permissions and delivery of alerts remain hosting responsibilities.

## Google OIDC and secure server sessions — B8.6.1

Default: `Authentication:Google:Enabled=false`. Enabling requires a registered Google **Web application** OAuth client, one controlled frontend/API HTTPS origin, restricted runtime PostgreSQL credentials and protected session keys. Invalid/incomplete activation fails startup. The integration uses [ASP.NET Core OpenID Connect code flow with PKCE](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-oidc-web-authentication?view=aspnetcore-10.0) and [Google's OIDC issuer/subject contract](https://developers.google.com/identity/openid-connect/openid-connect). Signature/Google keys, issuer, client audience, lifetime, protected state, nonce and callback correlation are validated by maintained middleware. Only the final `TicketReceived` event populates the verified source and calls `UpsertGoogleUserHandler`; `TokenValidated` is too early because protocol checks still follow it. Browser JSON/front-channel tokens are never accepted as verified identities.

Provide these values through protected deployment configuration/User Secrets, never repository files or command-line secrets. Environment keys use `Authentication__Google__` plus the suffix below (`:` becomes `__`):

| Suffix | Required value |
|---|---|
| `Enabled` | Explicit `true` only after provisioning the prerequisites |
| `ClientId` / `ClientSecret` | Real `.apps.googleusercontent.com` client ID and confidential client secret |
| `PublicOrigin` | One HTTPS origin, e.g. the deployment's `https://<controlled-host>`; no path, query, fragment or userinfo. Same-origin frontend only |
| `HttpsMode` | `Direct` for actual Kestrel TLS; `TrustedProxy` for an explicitly trusted TLS-terminating proxy |
| `TrustedProxyAddresses:0` (etc.) | Exact non-mapped proxy IPs, required only in TrustedProxy mode; no wildcard/network-wide trust |
| `ProxySanitizesForwardedHeaders` | Explicit `true` required in TrustedProxy mode: operator attests that the single proxy discards external forwarding headers and emits trustworthy client IP/scheme |
| `SessionMinutes` | 5–60, default 30; finite absolute session lifetime |
| `DataProtection:KeyRingPath` | Existing durable absolute directory outside application/source content root |
| `DataProtection:CertificatePath` / `CertificatePassword` | Existing private RSA PFX outside source content root and its protected password; certificate must be currently valid |

Register **exactly** `<PublicOrigin>/auth/google/callback` in the Google client. Callback is GET/query authorization code only; nonce/correlation cookies are Secure/HttpOnly/SameSite=Lax for the top-level redirect. No additional provider signout paths are enabled. Authorization/provider errors return generic coded Problem Details with trace ID; no code, token, cookie, raw exception or profile is serialized in logs/errors. Configure proxy/access-log exporters to omit authentication queries/headers as well.

| Route | Contract |
|---|---|
| GET `/auth/csrf` | Same-origin, no-cache JSON `{requestToken}`; sets Secure/HttpOnly/SameSite=Strict antiforgery cookie |
| POST `/auth/login` | Requires `X-CSRF-TOKEN` plus its cookie; revokes the previous MediPOS session, then challenges Google. Return target is fixed `/`; supplied targets other than `/` are rejected |
| GET `/auth/google/callback` | Middleware validates the complete OIDC response, upserts global user by `sub`, creates a new MediPOS session and redirects to `/` |
| GET `/auth/me` | Requires the protected MediPOS session; returns only `{userId}`. Missing/invalid session returns 401 without automatically challenging Google |
| POST `/auth/logout` | Requires a current antiforgery token/cookie; removes the server ticket and expires the application cookie, returning 204 |

Fetch a new antiforgery token after login because it is bound to the current identity. Logout ends the MediPOS session; it does not sign out the user's Google account. Host/HTTPS checks apply to authentication paths. Non-callback routes reject foreign Origin/cross-site fetches; callback CSRF protection is the middleware's state/nonce/correlation protocol. CORS is not enabled: no credentialed wildcard or alternate frontend origin. Authentication bodies are capped at 16 KiB. B8.6.1.1 replaces the shared 20-request auth-flow quota with separate client/operation quotas, evaluated before global admission. Limits use native ASP.NET Core fixed 60-second windows and concurrency leases; all queues are zero. Excess returns generic `429 auth.rate_limited`, no-cache, without client identifiers.

| Scope | Limit per process |
|---|---|
| Client bucket + login / callback / logout | 20 requests/minute **each**, independent quotas |
| Client bucket + session query / CSRF / other auth path | 60 / 30 / 10 requests/minute respectively |
| Client bucket, all auth operations combined | 60 requests/minute; rejected client requests never acquire the global minute quota |
| Client bucket concurrency | 2 auth requests, including at most 1 callback |
| Global concurrency | 4 auth requests, including at most 2 callbacks |
| Global auth volume | 120 admitted requests/minute; distributed overload can still exhaust this safety limit |

Client IPs map through a process-secret HMAC into exactly 1024 possible buckets. Native caches have at most 9216 client limiters plus 3 global and 7 no-op partitions (9226 total), regardless of address churn; no raw IP/header is a partition key or emitted log field. NAT clients and hash collisions share quotas; this conservative bounded policy does not promise perfect client isolation. All budgets reset on restart. One failed-callback client cannot exhaust the login quota; one slow callback cannot occupy all callback/auth slots. These initial single-VM limits still require external traffic/NAT/collision validation and proxy connection/request/DoS controls; they are not a distributed attack guarantee.

The `__Host-MediPOS.Session` cookie is protected by ASP.NET Core Data Protection, Secure/HttpOnly/SameSite=Lax, path `/`, no Domain. It contains a random server-ticket reference. The bounded 4096-ticket process-local store contains only the immutable MediPOS UUID and finite authentication properties; no Google access/refresh/ID tokens, email, roles, tenants or branches. Sliding renewal is disabled; a new OIDC login renews access with a fresh ticket. Logout invalidates copied cookies too. Restart drops server tickets and requires re-login; persistent keys preserve protection across restarts without making sessions distributed/durable. Multi-instance sessions/sticky routing are not implemented and require separate deployment design.

The key ring is certificate-encrypted using [ASP.NET Core Data Protection](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0). Hosting must protect the directory/PFX/secret with service-account ACLs, durable storage and protected recovery material, keep the decryption certificate available for existing keys and plan certificate/key rotation. Startup validates paths/certificate, not all filesystem ACLs or hosting backup controls. These controls are **external prerequisites**, not verified deployment readiness. Direct mode requires actual Kestrel TLS and derives the bucket only from the socket peer; browser forwarding headers are ignored. TrustedProxy mode verifies the socket peer against exact configured IPs **before** `UseForwardedHeaders` changes `RemoteIpAddress`, requires one literal `X-Forwarded-For` client address and exactly `X-Forwarded-Proto: https`, then verifies the forwarded result before rate limiting and OIDC. Missing/ambiguous headers and unknown peers fail closed with 403; `X-Forwarded-Host` and `Forwarded` are not trusted. Public Host remains checked against PublicOrigin. Automatic forwarding (`ASPNETCORE_FORWARDEDHEADERS_ENABLED`, `DOTNET_FORWARDEDHEADERS_ENABLED` or `ForwardedHeaders_Enabled=true`) is rejected at activation; no earlier forwarding middleware or additional proxy hop is supported.

The mandatory single proxy must **remove all external `Forwarded`, `X-Forwarded-*` and `X-Original-*` headers**, derive the client IP from its trusted connection, emit one client address and HTTPS scheme, preserve the approved Host, restrict backend access to the configured proxy and enforce external TLS, connection/request limits and sanitized access logs. The explicit sanitation setting records an operational prerequisite, not proof that the proxy complies. Controlled loopback HTTP fixtures validate application attribution/rejection only; actual proxy sanitation, socket topology, ACLs and capacity must be verified externally before activation.

Authenticated identity grants no tenant/platform authority. `ResolveAccessContextHandler` and the existing authorizer still read current membership/license/branch/schedule for each operation. `IPlatformAdministration` remains disabled by default and can be explicitly activated as described below; tax-delivery authority/provider remains disabled. No commercial/platform administration routes or additional user tables/migrations are introduced.

Local tests exercise actual HTTPS, OIDC and cookie middleware with **synthetic signing keys/provider transport and a fake user persistence port**; they certify configured rejection/composition, never Google's live keys/service or PostgreSQL. The same-email/different-sub PostgreSQL regression is prepared, not executed. Before deployment, an authorized external environment must register real client/callback/consent, provision runtime DB and protected keys, then test genuine Google consent/denial, code/PKCE exchange and key discovery, callback replay/missing correlation, concurrent first login and same-email distinct subjects, cookie expiry/logout/restart, proxy spoofing/origin/CSRF, log privacy and actual membership/license revocation. Record sanitized results; any failure blocks activation. A1–A2 and M8 remain incomplete, with platform/commercial/PWA/A18 and B8.2/B8.3/B8.4 external gates unchanged.

## Independent platform administration — B8.6.2

Default: no platform authority. `DisabledPlatformAdministration` remains the default implementation even with a valid Owner session. Activation requires the **Production** hosting environment, explicit valid Google OIDC/session activation, and protected hosting configuration:

| Configuration/environment key | Contract |
|---|---|
| `PlatformAdministration__Enabled` | Explicit `true`; absent/false leaves authority disabled |
| `PlatformAdministration__AdministratorUserIds__0` (and consecutive indices) | 1–32 unique non-empty internal User UUIDs in exact 36-character D format; no whitespace, email, Google subject, role, CSV or sparse/nested entries |

Never place real operator IDs or credentials in source, appsettings, deployment command lines or logs. An invalid enabled configuration fails startup with a generic error, never partial privileges. The immutable singleton allowlist is a startup snapshot, not a tenant role, a claim or a database privilege. `SessionPlatformAdministration` reads only the successful native MediPOS cookie authentication result and existing authenticated-user adapter, verifies the internal identity and issuance/expiry against server time, then returns the allowlisted UUID or null. Cancellation is honored. No email/profile/request header/query/body can grant authority. Existing `PlatformAdministrationAccess.RequireAsync` still rejects a differing audit ActorId.

To approve an operator, first let that person complete the legitimate Google flow so the global User is registered. Independently verify the SaaS operator's approval and the server-issued internal UUID from their authenticated `/auth/me` result against the authoritative registered identity; do not approve a freely supplied email/UUID or trust it without that verification. An authorized hosting operator adds the verified UUID to protected configuration and restarts the application. The application has no self-grant or allowlist-management endpoint. Approval of one UUID never grants another Google subject the same privilege, even when their emails match.

To revoke, remove that UUID, reindex the remaining entries and restart; to revoke all, explicitly disable platform administration. Verify that the changed process is running and that a fresh valid session is denied. Configuration changes do **not** revoke grants in the running snapshot. Restart also invalidates all process-local sessions and requires login again; it is not instantaneous hot revocation, nor cancellation of already committed/in-flight operations.
