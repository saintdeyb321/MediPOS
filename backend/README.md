## Google OIDC and secure server sessions — B8.6.1

Enabling requires a registered Google **Web application** OAuth client, one controlled frontend/API HTTPS origin, restricted runtime PostgreSQL credentials and protected session keys. Signature/Google keys, issuer, client audience, lifetime, protected state, nonce and callback correlation are validated by maintained middleware. Only the final `TicketReceived` event populates the verified source and calls `UpsertGoogleUserHandler`; `TokenValidated` is too early because protocol checks still follow it. Browser JSON/front-channel tokens are never accepted as verified identities.

Provide these values through protected deployment configuration/User Secrets, never repository files or command-line secrets. Environment keys use `Authentication__Google__` plus the suffix below (`:` becomes `__`):

| Suffix | Required value |
|---|---|
| `Enabled` | Explicit `true` only after provisioning the prerequisites |
| `ClientId` / `ClientSecret` | Real `.apps.googleusercontent.com` client ID and confidential client secret |
| `PublicOrigin` | One HTTPS origin, e.g. the deployment's `https://<controlled-host>`; no path, query, fragment or userinfo. Same-origin frontend only |
| `HttpsMode` | `Direct` for actual Kestrel TLS; `TrustedProxy` for an explicitly trusted TLS-terminating proxy |
| `TrustedProxyAddresses:0` (etc.) | Exact non-mapped proxy IPs, required only in TrustedProxy mode; no wildcard/network-wide trust |
| `ProxySanitizesForwardedHeaders` | Explicit `true` required in TrustedProxy mode: operator attests that the single proxy discards external forwarding headers and emits trustworthy client IP/scheme |
| `SessionMinutes` | 5–60, default 30; finite absolute session lifetime |
| `DataProtection:KeyRingPath` | Existing durable absolute directory outside application/source content root |
| `DataProtection:CertificatePath` / `CertificatePassword` | Existing private RSA PFX outside source content root and its protected password; certificate must be currently valid |

Callback is GET/query authorization code only; nonce/correlation cookies are Secure/HttpOnly/SameSite=Lax for the top-level redirect. No additional provider signout paths are enabled. Authorization/provider errors return generic coded Problem Details with trace ID; no code, token, cookie, raw exception or profile is serialized in logs/errors. Configure proxy/access-log exporters to omit authentication queries/headers as well.

| Route | Contract |
|---|---|
| GET `/auth/csrf` | Same-origin, no-cache JSON `{requestToken}`; sets Secure/HttpOnly/SameSite=Strict antiforgery cookie |
| POST `/auth/login` | Requires `X-CSRF-TOKEN` plus its cookie; revokes the previous MediPOS session, then challenges Google. Return target is fixed `/`; supplied targets other than `/` are rejected |
| GET `/auth/google/callback` | Middleware validates the complete OIDC response, upserts global user by `sub`, creates a new MediPOS session and redirects to `/` |

Fetch a new antiforgery token after login because it is bound to the current identity. Logout ends the MediPOS session; it does not sign out the user's Google account. Host/HTTPS checks apply to authentication paths. Non-callback routes reject foreign Origin/cross-site fetches; callback CSRF protection is the middleware's state/nonce/correlation protocol. CORS is not enabled: no credentialed wildcard or alternate frontend origin. Authentication bodies are capped at 16 KiB. B8.6.1.1 replaces the shared 20-request auth-flow quota with separate client/operation quotas, evaluated before global admission. Limits use native ASP.NET Core fixed 60-second windows and concurrency leases; all queues are zero. Excess returns generic `429 auth.rate_limited`, no-cache, without client identifiers.

| Scope | Limit per process |
|---|---|
| Client bucket + login / callback / logout | 20 requests/minute **each**, independent quotas |
| Client bucket + session query / CSRF / other auth path | 60 / 30 / 10 requests/minute respectively |
| Client bucket, all auth operations combined | 60 requests/minute; rejected client requests never acquire the global minute quota |
| Client bucket concurrency | 2 auth requests, including at most 1 callback |
| Global concurrency | 4 auth requests, including at most 2 callbacks |
| Global auth volume | 120 admitted requests/minute; distributed overload can still exhaust this safety limit |

Client IPs map through a process-secret HMAC into exactly 1024 possible buckets. Native caches have at most 9216 client limiters plus 3 global and 7 no-op partitions (9226 total), regardless of address churn; no raw IP/header is a partition key or emitted log field. NAT clients and hash collisions share quotas; this conservative bounded policy does not promise perfect client isolation. All budgets reset on restart. One failed-callback client cannot exhaust the login quota; one slow callback cannot occupy all callback/auth slots. These initial single-VM limits still require external traffic/NAT/collision validation and proxy connection/request/DoS controls; they are not a distributed attack guarantee.

The `__Host-MediPOS.Session` cookie is protected by ASP.NET Core Data Protection, Secure/HttpOnly/SameSite=Lax, path `/`, no Domain. It contains a random server-ticket reference. The bounded 4096-ticket process-local store contains only the immutable MediPOS UUID and finite authentication properties; no Google access/refresh/ID tokens, email, roles, tenants or branches. Sliding renewal is disabled; a new OIDC login renews access with a fresh ticket. Logout invalidates copied cookies too. Restart drops server tickets and requires re-login; persistent keys preserve protection across restarts without making sessions distributed/durable. Multi-instance sessions/sticky routing are not implemented and require separate deployment design.

The key ring is certificate-encrypted using [ASP.NET Core Data Protection](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0). Hosting must protect the directory/PFX/secret with service-account ACLs, durable storage and protected recovery material, keep the decryption certificate available for existing keys and plan certificate/key rotation. Startup validates paths/certificate, not all filesystem ACLs or hosting backup controls. These controls are **external prerequisites**, not verified deployment readiness. Direct mode requires actual Kestrel TLS and derives the bucket only from the socket peer; browser forwarding headers are ignored. TrustedProxy mode verifies the socket peer against exact configured IPs **before** `UseForwardedHeaders` changes `RemoteIpAddress`, requires one literal `X-Forwarded-For` client address and exactly `X-Forwarded-Proto: https`, then verifies the forwarded result before rate limiting and OIDC. Missing/ambiguous headers and unknown peers fail closed with 403; `X-Forwarded-Host` and `Forwarded` are not trusted. Public Host remains checked against PublicOrigin. Automatic forwarding (`ASPNETCORE_FORWARDEDHEADERS_ENABLED`, `DOTNET_FORWARDEDHEADERS_ENABLED` or `ForwardedHeaders_Enabled=true`) is rejected at activation; no earlier forwarding middleware or additional proxy hop is supported.

The mandatory single proxy must **remove all external `Forwarded`, `X-Forwarded-*` and `X-Original-*` headers**, derive the client IP from its trusted connection, emit one client address and HTTPS scheme, preserve the approved Host, restrict backend access to the configured proxy and enforce external TLS, connection/request limits and sanitized access logs. The explicit sanitation setting records an operational prerequisite, not proof that the proxy complies. Controlled loopback HTTP fixtures validate application attribution/rejection only; actual proxy sanitation, socket topology, ACLs and capacity must be verified externally before activation.

Authenticated identity grants no tenant/platform authority. `ResolveAccessContextHandler` and the existing authorizer still read current membership/license/branch/schedule for each operation. `IPlatformAdministration` remains disabled by default and can be explicitly activated as described below; tax-delivery authority/provider remains disabled. No commercial/platform administration routes or additional user tables/migrations are introduced.

The same-email/different-sub PostgreSQL regression is prepared, not executed.
