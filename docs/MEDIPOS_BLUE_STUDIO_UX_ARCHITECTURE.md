## 2. UAX1 — Arquitectura de presentación y patrones compartidos

### 2.1 Sistema de diseño, no estilos por página

Mantener React 19 + TS + React Router + TanStack Query + Tailwind 4 + Lucide, comprobados en package.json. `app → features → shared`, shared sin imports de features. Usar composición de slots/children y variantes tipadas; no herencia de clases React, no mega componente configurable con docenas de flags, no factory universal de CRUD. Mantener tokens.css/ @theme inline como fuente única. `base.css`, `ui.css`, `operations.css` y layouts: reducir solapamientos demostrados y reglas sin consumidores; no crear otro stylesheet global competidor. Tailwind para composición local y tokens semánticos, CSS común para comportamiento complejo, sin duplicar utilidades. No propagar CSS con !important. No inline styles repetidos salvo datos dinámicos justificados. Aplicar SOLID donde aporte: componentes presentacionales sin lógica de permisos/HTTP, feature dueño de su estado y operaciones, interfaces pequeñas. Extraer repetición estable, no crear abstracciones para similitudes accidentales. Eliminar imports, componentes, variantes y CSS que queden sin uso únicamente tras comprobar referencias estáticas/dinámicas, rutas, impresión y pruebas; no borrar código por un conteo de coincidencias aislado. No dejar versiones legacy paralelas de un patrón migrado salvo compatibilidad justificada. Conservar Blue Studio (`#0B2340`, `#075EA8`, `#EAF3FA`, `#38BDF8`, `#F59E42` y semánticos existentes). No otro cambio de marca.

Usar existentes PageHeader, PageToolbar, FilterBar, Panel, FormSection, FormFooter, Button, TextField, ActionMenu, Modal/Drawer, Dialog, Badge, Notice, PageControls, States, MetricCard, BackLink y Breadcrumbs. Componerlos para los patrones siguientes. Solo extraer nueva primitiva si no hay equivalente y aporta reutilización o accesibilidad real. Nombres ilustrativos: DataSection (título opcional, tabs, toolbar, contenido, footer), HelpPopover (icono con nombre accesible), FieldGroup (label/control/hint/error), EditorLayout (cabecera, formulario, resumen, acciones). No imponer esos nombres si existentes pueden cubrirlo. Un componente de tabla compartido puede ser un contenedor con slots semánticos; no reescribir todos los renderizadores en un motor genérico. Datos y permisos quedan en feature.

### 2.2 Cuatro patrones de página (contrato de composición)

**A. Directorio/listado:** PageHeader compacto (título, y acción global solo cuando realmente aplica a toda la página), una DataSection: pestañas, filtros y acciones contextuales dentro, tabla o tarjetas según caso, pie con paginación. Las acciones de un conjunto de datos se colocan junto a ese conjunto, no como enlaces flotantes; no duplicar acciones entre cabecera y toolbar. No paneles vacíos apilados ni cabeceras duplicadas. Ejemplos: Productos, Inventario, Transferencias, Personal, Auditoría, Boticas Superadmin. La tabla es la protagonista. En 1366×768 con sidebar abierta y zoom 100%, en un directorio poblado ordinario se deben ver cabecera de tabla y al menos 4 filas estándar sin scroll de página, si hay datos suficientes y no hay alerta crítica; objetivo 5–7 filas. No forzar altura o fuentes para cumplir; medir screenshot. Objetivo cabecera + controles de directorio <= 220 px desde inicio del contenido, sin alertas extraordinarias. No límite artificial de altura de tabla; tabla usa ancho disponible. Si se limita scroll, hacerlo en región con etiqueta y foco; encabezado sticky cuando útil. No hacer overflow:hidden para esconder desbordamiento. Priorizar columnas por valor operativo; conservar identidad, estado/importe/cantidad y acción en móvil cuando correspondan, trasladar secundarios a detalle accesible o scroll local. No ocultar campos indispensables ni transformar toda tabla en tarjetas por defecto. Paginación junto a la tabla, no debajo de bloques de ayuda.

**B. Editor/transacción:** flecha con texto «Volver a [módulo]», título de tarea, estado relevante, campos por secciones, contenido principal y resumen lateral compacto solo cuando aporta valor. Sin lista ni botones de creación que compitan con editor activo. Escritorio grid `minmax(0,1fr)` + resumen de ~280–340 px según ancho útil; tablet/móvil una columna, resumen y acción final accesibles sin solaparse. Barra de acciones consistente; si sticky, no tapar contenido ni teclado móvil. Guardar borrador/confirmar solo según contrato. Back conserva o advierte cambios; no usar `navigate(-1)` a ciegas, destino explícito seguro y restauración de filtros/posición cuando proceda. No reset de intención pendiente. Verificar ruta directa, refresh, atrás/adelante y cambio de contexto. Definir claramente las vistas consulta → alta/detalle → confirmación/acuse → retorno; mantener una sola tarea primaria. No duplicar botón Nuevo ni reemplazar la intención activa por otra. Una confirmación de abandono solo si hay cambios realmente perdibles y el contrato permite abandonar; estado incierto exige recuperar la operación original. No introducir wizard por costumbre ni eliminar una etapa necesaria de negocio.

**C. Resumen/dashboard:** métricas reales, pocas tarjetas con etiquetas y acciones útiles, secciones por tarea. No KPIs globales inferidos de página, ni valores en cero inventados, ni gráficos decorativos. Mostrar carga/error/vacío sin desplazar violentamente contenido. Usar color semántico acompañado de texto.

**D. Bandeja/configuración:** bandeja lista-detalle para notificaciones/actividad y tarjetas/secciones para configuración/acceso. Filtros compactos, detalle en drawer o panel adaptable, tarjetas con nombre/estado/acción. No abusar de tablas para todo. La información técnica queda en detalle de soporte o ayuda contextual.

Si se necesita `ProductDetail` para operación o validación, obtenerlo una sola vez, validar respuesta/identidad/actividad según contrato; no suprimir validación por clic. Inventario debe conservar filtro permitido para saldo/lote de producto inactivo cuando el contrato lo permita; comprobar límites de search activo y ofrecer modo alternativo autorizado o registrar brecha, no ocultar stock existente. En compras admitir producto activo sin stock. No convertir búsqueda de POS en filtro de mantenimiento sin equivalencia. Evitar GET detalle de cada opción; ProductLabel ya cachea, medir N+1 de etiquetas de tabla; compartir caché válida sin inventar nombres, documentar brecha proyección/batch si datos faltan. No añadir endpoint automáticamente.

## 4. UAX3 — Compras, Transferencias, POS y Caja

### Compras

Inicio de módulo: cabecera `Compras | + Nueva recepción`, buscador compacto «Buscar por referencia» y resultados reales con estado, fecha y abrir. Proveedores como acción/tab solo si útil y acceso real; no botón aislado sin contexto. En la pantalla inicial, una superficie de búsqueda y resultados, con estado inicial orientado a la tarea; sin gran acordeón abierto, campo de ancho total ni resumen vacío. `purchasing/api.ts` tiene GET por ID, búsqueda por referencia y proveedores; NO listado general. No simular historial, registros recientes ni contadores. Presentar «Buscar una recepción» como tarea normal y «Buscar por código de soporte» en sección avanzada bajo demanda. Si falta historial general, proponer endpoint paginado y filtros como brecha funcional separada. No confundir referencia con identificador único. Mensajes técnicos al soporte, no a la vista habitual.

Al iniciar recepción cambiar a patrón B (misma ruta con estado/params existentes o subvista coherente; preservar deep links/receiptPending). Flecha «Volver a compras» visible; no mantener buscador/acción Nueva recepción encima del editor. Secciones: proveedor y comprobante/referencia (opcionales de verdad, no inventar RUC), productos y lotes, resumen y acción «Confirmar recepción». Reemplazar el wizard de cuatro pantallas por un editor coherente con secciones progresivas; no exigir cuatro navegaciones solo para presentar información. Si una transición real requiere un borrador/ID o validación previa, habilitar la siguiente sección mediante la acción necesaria y mostrar progreso inline, sin ocultar o saltar la transición ni inventar una escritura única. El recorrido usual no debe mostrar los controles de recuperación excepcional, enlaces de ayuda extensos ni otra acción Nueva recepción mientras edita. Ayuda contextual junto a referencia/confirmación. No exigir proveedor, comprobante o datos fiscales inexistentes. Crear borrador una sola vez en momento permitido por contrato (p.ej. acción de añadir/guardar tras datos iniciales); no crear al montar, no guardar con cada tecla. Si existe requisito de ID para líneas, coordinar la primera creación con el mismo receipt hook y mostrar continuidad; no fingir que un único botón equivale a un único POST o transacción. Guardar líneas con revisión/versión, confirmar llegada real con acción consciente, no auto-confirmar stock. Los estados `draft` y `confirmed` son estados del servidor. Confirmada: acuse + volver al listado/buscar u otra recepción explícita. Si pierde respuesta, misma intención/recibo; no permitir crear otra recepción ignorando pendiente. Resumen sticky solo si no corta acciones; móvil bajo líneas, total visible. Conservar protección de navegación, edición, errores por línea, lotes y FEFO. Proveedor integrado select/búsqueda, alta reutiliza formulario sin modales superpuestos innecesarios.

### Transferencias mercadería y efectivo

Un mismo patrón de directorio: título «Transferencias», tabs/selector contextual «Mercadería | Efectivo entre cajas» enlazando rutas existentes, acción primaria según tipo y permisos. Toolbar filtros sede/estado/dirección si contrato lo soporta; no enviar parámetros ficticios. Tabla origen→destino, estado, fecha, acción Ver; badges semánticos reales. Detalle/solicitud/recepción en patrón B o drawer apropiado; volver conserva filtros. Bloque de recuperación excepcional cerrado fuera de vista habitual, botón accesible de soporte; si intención pendiente, aviso visible y acción de consultar original, no esconder con colapso. Mantener cada transición de custodia (solicitar/aprobar/despachar/recibir/cancelar) según actor, origen, destino y estado. Nunca combinar despachar/recibir en un clic ni cambiar stock/caja antes de confirmación. Para efectivo conservar saldo, cierre y dueño de caja, UUID e idempotencia. Mostrar importes y cantidades legibles. Si faltan sedes elegibles, estado vacío explica por qué no puede transferir, sin inventar sedes.

### POS y Caja

POS no se fuerza a layout de directorio: búsqueda/lector/catálogo compacto y carrito/total fijo lógico (desktop) o resumen accesible en móvil, teclado y shortcuts existentes, cobrar con importe explícito, vuelto visible. Preservar precisión decimal, pagos, vendedor, ticket interno, recuperación, offline, impresión y estados de caja. No animar lectura de código ni bloquear por estética. Caja y arqueos: estado abierto/cerrado visible en cabecera, acción principal correspondiente, métricas compactas de importes reales (efectivo esperado/contado/diferencia según etapa y permiso), movimientos y arqueos en listados o pestañas coherentes según rutas/contrato. Cierre y arqueo en editor explícito con etiquetas, importes alineados, diferencia visible y acción final inequívoca; no mezclar apertura, cierre y consultas como formularios simultáneos. No esconder diferencias o deshabilitar controles sin explicación. Mantener motivo de anulación, saldo, reconciliación y acuses. No reintroducir casillas redundantes ni repetir GET optimizados. Probar lector simulado y físico si disponible, teclado, pagos y reenvío incierto; no emitir CPE real.

Una toolbar compacta con filtros alineados, sin checkbox y contadores dispersos ni bloques de texto de ancho total. ## 6. UAX5 — React, calidad, validación y entrega real

### Estado, red y seguridad

Usar React declarativo: derivar vista desde estado mínimo, no efectos para copiar props/queries a otro estado sin necesidad. Estado local de filtros/formulario en feature, estado servidor en TanStack Query; no introducir Redux/Zustand ni contextos globales para todo. No memoización indiscriminada. Revisar re-renders por perfil solo si hay evidencia. Query keys con sesión/actor/membresía/tenant/sucursal, `enabled` según contexto, AbortSignal, caché acotada, invalidación selectiva tras acuse válido, stale/focus/reconnect según riesgo. Reutilizar directorios si ámbito coincide. No ocultar errores mostrando datos antiguos como actuales; no disparar polling agresivo ni refetch masivo; no auto-retry de escrituras. Mantener los hooks de recuperación/HTTP/decimales existentes, URL de intención, protección de navegación, permisos, CSRF, exactitud, RLS, versiones, offline, licencia y horarios. No borrar marcadores de usuario al cambiar pantalla. No sustituir confirmación de servidor por estado optimista irreversible. No realizar cambios backend/contratos/esquema/DEV datos/S4/OAuth/SUNAT/CI. CPE desactivada. Registrar brechas contractuales como pendientes separados, no falsificar funcionalidades. Usuario autoriza librerías útiles, pero por defecto no añadir; cualquier adición requiere justificación concreta, versión compatible, licencia comercial, diff lockfile y auditoría. No subir código o datos privados.

### UX writing

| Texto técnico/verboso | Redacción objetivo (adaptar al caso real) |
|---|---|
| «La API permite buscar una referencia documental…» | «Busca por número o referencia del comprobante.» |
| «Referencia documental… no representa una clave de idempotencia» | «Referencia del comprobante (opcional)»; ayuda: «Te ayudará a encontrar esta recepción.» |
| «Borrador persistido» | «Borrador» |
| «No es un error de consulta» | Eliminar; distinguir estado vacío por diseño. |
| «Cómo interpretar stock, mínimos y movimientos» | Icono de ayuda junto al stock; explicación breve de unidades y alcance. |
| «Filas de esta página» | Eliminar si no aporta; si cuenta útil, «20 productos en esta página». |
| «Referencia de fechas: … Lima» | Solo en filtro/ayuda de vencimientos cuando influye en interpretación. |
| «Resultado pendiente de conciliación operacional…» | «No pudimos confirmar el guardado. Consulta el resultado antes de repetir la operación.»; conservar detalle y referencia en ayuda de soporte. |
| «Lecturas personales de tu membresía» | «Tus avisos»; «Marcar como leído no resuelve la alerta» donde corresponda. |
| «Configurar entidades y sucursales (solo Owner)» | «Gestionar sucursales» / «Crear mi primera sucursal» para propietario autorizado. |

No quitar avisos críticos ni labels necesarios. Terminología: preferir «sede» en interfaz cotidiana y «botica» para negocio cuando sea correcto; no renombrar DTO/API ni confundir razón social con sede. Usar un mismo verbo por acción (p. ej., «Confirmar recepción»). Cada texto debe permitir decidir, actuar, comprender un dato o recuperarse de un problema: si no, eliminarlo; si es útil solo bajo demanda, HelpPopover/detalle de soporte; si afecta una decisión, mantenerlo visible. Evitar traducciones literales, redundancia, API, DTO, idempotencia, UUID y mensajes internos en el recorrido habitual. Mensajes cortos, consistentes, orientados a tarea; soporte puede desplegar traceId/código técnico sin exponer secretos. No ocultar términos semánticamente necesarios. No reintroducir botones Actualizar rutinarios. Recuperación/Reintentar y sincronización explícita son acciones reales, conservar.

### Validación verificable (no confundir reflow con calidad)

1. Baseline: comprobar qué HTML/JS/CSS sirve localhost; capturar 1366×768 y móvil de patrones principales si entorno permite. Si DEV es viejo, usar build del SHA en navegador aislado con fixtures para comparación; no reiniciar instancia ni borrar almacenamiento sin permiso. Registrar fuente/fixture/viewport/huella del árbol. Conservar evidencias privadas fuera del repo.
2. Check visual por módulo: revisar manualmente o con navegador automatizado cada ruta y vista secundaria con datos representativos, no solo vacíos. A 1366×768 ver encabezado y >=4 filas normales en directorios poblados (objetivo, justificar excepción); a 1920×1080 no estirar campos sin razón; a 768×1024, 390×844, 320×640, horizontal 844×390 y zoom 200%, reflow sin scroll horizontal global (tablas pueden tener región local), textos y acciones no recortados, contraste, foco, labels, popover, modales, teclado, sticky sin cubrir contenido. Para componentes compartidos probar todas las variantes representativas; en resto cada ruta base en desktop/móvil y estados críticos. Reusar matriz previa solo para builds/consumidores intactos. No repetir el producto cartesiano de todas las rutas/estados/resoluciones si no aporta; ampliar cuando cambio compartido o defecto. Registrar fallos, arreglar y volver a capturar el afectado. Comparar antes/después con misma ruta, rol, fixture, viewport, zoom y sidebar; si no existe baseline equivalente, declararlo. Revisar alineación de bordes, ritmo vertical, jerarquía, espacio ocupado por controles, filas visibles, acciones agrupadas, legibilidad y calidad de estados vacíos; no aprobar mediante screenshots de una pantalla sin datos. Los 220 px y 4 filas son metas de producto para un directorio ordinario, no normas WCAG/Nielsen ni obligación de reducir accesibilidad. Para rendimiento percibido, medir en recorridos comparables solicitudes, clics y estabilidad de layout, no confundir fixture con latencia de producción.
3. Heurísticas de Nielsen: visibilidad de estado (loading/guardado/pendiente), lenguaje del usuario, control/volver, consistencia, prevención de error, reconocer en vez de recordar, eficiencia, mínimo ruido, recuperación y ayuda. Verificar WCAG 2.2 AA como objetivo (contraste normal 4.5:1, no texto 3:1 cuando aplica, foco, reflow, teclado, nombres accesibles, no solo color, objetivo táctil 44px preferido). No declarar conformidad completa sin auditoría. No quitar controles de accesibilidad para ahorrar altura.
4. Funcional: pruebas DOM focalizadas al migrar patrón. Buscar/seleccionar por teclado; categoría/estado/paginación; limpiar filtro; detalle/volver mantiene contexto; no resetea borrador ni dispara POST al navegar; resultado incierto conserva ID/clave; actor/scope; reentrada; precio/cantidad exacta; flujo compras/stock, custodia, caja y avisos; PWA e impresión. Mantener aserciones de negocio, actualizar selectores/copy con intención justificada. No quitar pruebas para conseguir PASS. Medir GET/POST por recorrido con fixtures iguales (no prometer latencia real); no aumentar lecturas sin explicación. Registrar tamaño JS/CSS gzip antes/después si comparable; justificar crecimiento real, sin instalar otro runtime por estética. No metas artificiales de reducción de líneas.
5. Aceptación por tareas (evidencia mínima, con datos controlados): Productos: cambiar tab, buscar/filtrar, paginar, alta/edición e importación según permiso; Inventario: buscar/seleccionar/limpiar, cambiar tab, abrir recepción y volver; Compras: consulta, nueva, líneas/lotes, confirmar, volver y recuperación incierta; Transferencias mercadería/efectivo: listado, detalle y transiciones por rol; POS/Caja/arqueos: lector/teclado, pago, cierre/diferencia, ticket y recuperación; Notificaciones: filtros, lectura, detalle y acción; resto: al menos una tarea principal por familia y cada ruta/rol relevante según matriz. Simular errores y recarga donde afecten escritura. Contar clics desde el mismo inicio/fin, sin omitir controles de seguridad; documentar comparaciones no posibles. No ejecutar escrituras reales sobre DEV sin autorización. Si un recorrido no puede verificarse, marcar pendiente con causa, no PASS.
6. Cierre frontend: `npm run build`, `npm run lint`, `npm run test`, `git diff --check` sobre árbol final. Reportar conteos exactos por suite y cualquier FAIL/SKIP. GO técnico de candidato requiere build/lint/diff limpios, sin fallos ni pruebas requeridas omitidas; si hay skips preexistentes o no aplicables, identificarlos, no convertirlos en PASS ni crear trabajo fuera del alcance para ocultarlos. Un bloqueo de prueba requerida implica NO-GO para el gate correspondiente. Backend intacto → no suites backend locales por estética; CI integral del SHA publicado sigue siendo gate posterior. No ocultar tests intermitentes. Identificar HTML/assets/hash de candidato. Si DEV requiere reinicio, solicitar autorización exacta o usar la vigente que cubra explícitamente la instancia actual y comprobar ausencia de escrituras; iniciar HTTPS con configuración privada intacta y `ProductImportRecovery__EnabledAfterWriterDrain=false` mientras esquema 39/writer drain no acreditado. No tocar DB, migraciones ni almacenamiento PWA; verificar readiness y hashes servidos, Google legítimo con operador si necesario. Si no se autoriza, BUILD_LISTO_PENDIENTE_REINICIO, no declarar actualizado. Capturas con fixtures ≠ Chrome autenticado. Aceptación visual del operador y pruebas comerciales se registran aparte.

## 7. Entrega y criterio de terminación

Ejecutar UAX1→UAX5 automáticamente, no esperar otro prompt entre grupos. Si una brecha contractual o entorno bloquea una tarea, registrar exacto endpoint/DTO, requisito, prueba, propuesta mínima y continuar todo lo independiente. No declarar una búsqueda global o historial completo sin backend. No abrir otra refactorización general. Actualizar `frontend/AGENTS.md` con reglas permanentes compactas (composición A–D, ayuda, UX writing, contratos y aceptación visual); integrar con las ya existentes sin duplicarlas ni borrar restricciones. `docs/CURRENT_STATE.md` único checkpoint y evidencia. Diferenciar IMPLEMENTADO, VERIFICADO, BLOQUEADO y PENDIENTE; un módulo solo está verificado cuando pasa los criterios aplicables de composición, navegación, estados, contrato, responsive y tareas. No declarar UAX terminado si queda una ruta requerida sin implementar. Separar GO de código/build, GO visual (navegador y aceptación del operador), estado DEV y gate de publicación (CI y autorizaciones posteriores). Entrega breve: (1) qué módulos y primitivas se migraron, (2) antes/después visual con dimensiones, (3) clics y GET/POST comparables, (4) PASS/FAIL/SKIP, (5) build y localhost identificados, (6) brechas backend/externas exactas, (7) GO/NO-GO para publicar y para aceptación; no declarar producción lista. Nada de nuevos planes gigantes, informes repetidos ni promesas. No tocar GitHub sin autorización. Si falta contexto, guardar checkpoint y continuar al restablecer; no volver al inicio.
